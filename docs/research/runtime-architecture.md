# Rust runtime and terminal investigation

Research date: October 30, 2026 (Asia/Tehran). Reference product: GitKraken Desktop 12.6.1. Status: research complete for architectural planning; recommendations below remain proposed, and no runtime has been implemented or benchmarked.

## Finding

The chosen Tauri + Rust + React stack has suitable building blocks. The main design task is making application operations, their real execution history, interactive shells, and refreshed repository state agree. A terminal widget by itself does not provide that contract. The desktop core should own the processes and recording so that collapsing the panel cannot stop them. This is an architectural recommendation inferred from the documented process, IPC and terminal APIs below.

## Verified mechanisms and implications

| ID | Primary-source fact | Implication for this project; proposals are identified |
| --- | --- | --- |
| RUNTIME-01 | Tauri commands invoke Rust functions; channels are the recommended facility for streams. A Rust channel can continue sending multiple serialized messages after command completion. [Calling Rust](https://v2.tauri.app/develop/calling-rust/), [Channel API](https://docs.rs/tauri/latest/tauri/ipc/struct.Channel.html) | **Proposed:** submit typed operations and subscribe to structured progress. Supply replay from a journal after a window/subscriber reconnect; an IPC stream alone is not durable history. Generate or check frontend types against the Rust schema during implementation. |
| RUNTIME-02 | Rust passes `Command::arg` values directly, without shell expansion. The program and arguments are distinct. Its debug display is not guaranteed to be a runnable shell command; Windows `cmd.exe` and batch decoding need particular care. [Rust Command](https://doc.rust-lang.org/std/process/struct.Command.html) | **Proposed:** launch an explicitly resolved Git executable with an argument vector and working directory. Derive the displayed command from that vector using a named shell formatter; retain structured arguments as the authority. Never execute the displayed string. Account separately for Git option and pathspec interpretation. |
| RUNTIME-03 | Tokio provides asynchronous child creation and pipe access. Its documentation warns about deadlocks if writing stdin and draining output are not coordinated. [Tokio process](https://docs.rs/tokio/latest/tokio/process/) | **Proposed:** concurrently drain stdout and stderr as bounded byte chunks, feed stdin when needed, and wait for exit and stream closure. Record stream identity and observed sequence; separate pipes cannot establish an exact global ordering of the child's original writes. Use carriage-return-aware rendering for progress. |
| RUNTIME-04 | `portable-pty` exposes platform PTYs, process launch and child handles. `MasterPty` supports resize and standard `Read`/`Write` handles. [Crate](https://docs.rs/portable-pty/latest/portable_pty/), [MasterPty](https://docs.rs/portable-pty/latest/portable_pty/trait.MasterPty.html), [Child](https://docs.rs/portable-pty/latest/portable_pty/trait.Child.html) | **Proposed:** use it for interactive PowerShell/Bash sessions behind xterm.js. Bridge blocking PTY I/O off the UI thread and outside async executor threads that must stay responsive. Keep these session handles separate from application Git steps. |
| RUNTIME-05 | xterm.js processes writes asynchronously; an excessively fast producer can outpace its buffers. Its guide describes acknowledgement and high/low watermark flow control. [Flow control](https://xtermjs.org/docs/guides/flowcontrol/) | **Proposed:** batch terminal output and implement bounded queues with acknowledgements across the Rust-to-webview bridge. Test flood output, resize and interrupt responsiveness together. Do not assume Tauri IPC automatically supplies end-to-end terminal backpressure. |
| RUNTIME-06 | xterm.js accepts strings as UTF-16 and byte arrays as UTF-8; its decoder handles multibyte characters split across chunks. Non-UTF-8 terminal environments require transcoding. [Encoding](https://xtermjs.org/docs/guides/encoding/) | **Proposed:** define terminal encoding per session, send compatible byte chunks and preserve decoder state. Git machine-output parsing and terminal text decoding are different adapters. Test both Unicode text and a configured legacy shell encoding. |
| RUNTIME-07 | Dropping a Tokio child does not stop it by default. `start_kill` does not wait; asynchronous `kill` does wait. [Process caveats](https://docs.rs/tokio/latest/tokio/process/), [Child lifecycle](https://docs.rs/tokio/latest/tokio/process/struct.Child.html) | **Proposed:** processes have explicit owners, cancellation and shutdown policies; every started child is awaited. A cancelled request or destroyed React component does not imply process termination. Do not label interruption as rollback. |
| RUNTIME-08 | Windows job objects can contain processes and normally their children, with documented breakaway exceptions; an entire job can be terminated. Rust's Unix command extension supports process-group assignment. [Windows jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Unix CommandExt](https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html) | **Proposed:** prototype OS-specific process-tree control for Git, hooks, SSH helpers and terminals. Killing only the immediate child is insufficient evidence that all descendants have stopped. Graceful interruption, escalation, and repository recovery require distinct outcomes. |
| RUNTIME-09 | Linked worktrees have private Git metadata and a shared common directory; references and configuration have defined sharing rules. Git recommends resolving metadata paths through its commands rather than guessing paths. [Worktree documentation](https://git-scm.com/docs/git-worktree) | **Proposed:** use common-directory identity for cross-worktree coordination, with per-worktree state nested beneath it. Start with conservative serialization of application writes that share a repository; classify safe parallel reads later from evidence. An internal queue cannot lock out external terminals. |
| RUNTIME-10 | `git status` normally refreshes the index and can contend with concurrent writers. `GIT_OPTIONAL_LOCKS=0` disables optional lock-taking suboperations. [Status background refresh](https://git-scm.com/docs/git-status#_background_refresh), [Git environment](https://git-scm.com/docs/git) | **Proposed:** use optional-lock suppression for background reads where appropriate, reconcile after operations, and handle real lock conflicts as observable results. Do not disable mandatory Git locking or silently remove lock files. |
| RUNTIME-11 | Filesystem watcher behavior varies: notify documents network/WSL gaps, editor save patterns and polling alternatives. [notify](https://docs.rs/notify/latest/notify/) | **Proposed:** treat events as invalidation hints and derive state from Git snapshots. Debounce and coalesce refresh requests; reconcile on focus, operation completion and watcher recovery. Watch both worktree and relevant common metadata. Avoid deriving final repository truth from the event stream. |
| RUNTIME-12 | Git porcelain status has machine formats, and `-z` returns unquoted pathnames with NUL delimiters. Rust OS strings can be non-Unicode, while lossy conversion replaces invalid sequences. [Status format](https://git-scm.com/docs/git-status#_porcelain_format_version_2), [OsStr](https://doc.rust-lang.org/std/ffi/struct.OsStr.html) | **Proposed:** retain native paths/bytes in Rust and send opaque path identifiers plus a display label to React. Reversible platform-specific encoding is another option to evaluate. Never use a lossy display label as the path passed back to Git. Test newlines, tabs, quotes, leading dashes and non-UTF-8 names where the OS permits them. |
| RUNTIME-13 | Git credentials can come from helpers and askpass programs, with terminal prompts as a fallback. `GIT_TERMINAL_PROMPT=false` suppresses Git's terminal prompting. [Credential flow](https://git-scm.com/docs/gitcredentials), [Git environment](https://git-scm.com/docs/git) | **Proposed:** support an explicit interaction broker for application-driven auth while preserving compatible configured helpers. Background jobs must not hang on an invisible prompt. Interactive terminals retain a shell interaction path. SSH passphrases, host-key confirmation, OAuth and signing prompts need individual validation rather than one generic password dialog. |
| RUNTIME-14 | Hooks can veto commits and change commit messages. Git exposes editor and sequence-editor overrides, and signing supports configured programs/formats. [Hooks](https://git-scm.com/docs/githooks), [Git environment](https://git-scm.com/docs/git), [Signing config](https://git-scm.com/docs/git-config#Documentation/git-config.txt-gpgformat) | **Proposed:** preserve hooks, signing and identity semantics. Use operation-scoped editor/sequence-editor bridges for graphical workflows where needed, not global configuration rewrites. Report hook failure and modified messages truthfully. Verify continued/retried operations after a prompt or conflict. |
| RUNTIME-15 | Tauri capabilities constrain window/plugin access, but registered custom commands are available to all app windows by default unless configured otherwise. Capabilities do not validate unsafe Rust implementation logic. [Capabilities](https://v2.tauri.app/security/capabilities/) | **Proposed:** expose repository operations rather than a generic frontend arbitrary-process command. Validate repository handles, paths and inputs in Rust; explicitly configure custom-command access. Render repository-sourced text as data. This is necessary for a Git client handling arbitrary commit messages and file contents. |

## Proposed runtime boundary

This is a candidate for the execution-contract prototype, not an accepted interface:

| Module boundary | What callers ask for | Behavior hidden inside |
| --- | --- | --- |
| Repository coordinator | Open repository; observe snapshot; perform a Git intent | Common-directory discovery, worktree identity, queued mutation, stale-generation handling, snapshot reconciliation |
| Operation service | Submit operation; observe/cancel it; supply requested interaction | One or more real execution steps, child ownership, error classification, conflict/recovery states, provider requests |
| Action journal | Read events after a cursor; subscribe; export a redacted history | Persistent ordering, credentials/output redaction, replay, retention and interrupted-operation recovery |
| Terminal sessions | Open/input/resize/close a repository-bound session | PTY ownership, shell configuration, output flow control and terminal lifecycle |

Candidate event fields are operation ID, step ID, repository/worktree ID, event sequence, timestamp, origin, typed payload and schema version. An execution-start payload describes the actual executable/arguments/cwd; output events identify a stream and chunk; a completion event records process status separately from the repository outcome. A merge conflict can leave the repository awaiting resolution after Git has exited. A provider request or UI-only action needs its own activity type, not an invented Git command.

**Important limit:** PTY output is terminal data, not a structured shell execution log. Parsing echoed lines cannot reliably identify aliases, pipelines, builtins, multiline input, scripts, nested shells or descendant processes. Exact capture of application-generated Git commands is feasible through the runner. Shell-command capture requires a separately defined shell integration and support matrix. This distinction follows from the PTY API's byte-stream interface; it has not been validated with a prototype.

Redaction must happen before persistence and delivery where practical, including known credential values in arguments, URLs and outputs. Arbitrary tools can print previously unknown secrets, so universal perfect output redaction must not be claimed. Decide raw-output persistence, protected storage, retention, truncation/spooling and export behavior explicitly. When the view falls behind, recording must continue with a truthful indication of any deliberate output omission; a hidden panel cannot silently discard history.

## Packaging and platform work

Tauri supports Windows MSI through WiX and setup executables through NSIS. Its guide identifies Windows/MSVC requirements and cross-compilation caveats; MSI builds have a VBScript requirement. Decide installer format and WebView2 distribution behavior after the first native build. No MSI optional-feature query or change was made here. [Windows installers](https://v2.tauri.app/distribute/windows-installer/).

macOS signing/notarization and Linux package formats are separate distribution work. Windows-first development does not validate those targets; plan real OS test hosts and platform-specific shell/PTY/path fixtures. Packaging, update identity and signing material remain unconfigured. [Distribution](https://v2.tauri.app/distribute/).

## Next prototype and unresolved decisions

1. **Execution and replay:** run a real temporary-repository operation, hide/unmount/reopen the panel, and show identical commands, status and captured output after replay. Restart recovery must distinguish an interrupted observer from a known process exit. Decide recording retention and whether “always record” includes background reads, local UI actions and shell command metadata.
2. **Interaction:** demonstrate a failing hook, editor request and synthetic credential prompt without real secrets. Prove that ordinary stdout containing the word “password” is not misclassified as an authentication protocol. Choose the trusted askpass/editor bridge mechanism.
3. **Cancellation:** exercise long-running children and a hook-created descendant on Windows, then equivalent Unix process groups. Verify that cancellation is truthful and leaves actionable Git state; do not automatically reset repositories to make cancellation look successful.
4. **Concurrent worktrees:** queue writes across two worktrees, externally change a reference, and reconcile after a lock conflict. Decide how much independent mutation to permit after conservative correctness is established.
5. **Streams and paths:** stress bounded output with split UTF-8, carriage returns, large stderr and slow UI consumption. Test malicious-looking literal names and OS-specific non-Unicode paths, preserving native identity through the UI boundary.
6. **Delivery prerequisites:** locate/install an appropriate Rust MSVC toolchain in an authorized implementation step, then build and open a minimal Tauri window using the available native tooling. Choose supported Git version/distribution and OS/CPU support targets. The prototype must not treat the old local GitKraken as the pinned reference.

Suggested repository fixtures also include unborn HEAD, detached HEAD, rename plus partial staging, merge and rebase conflict/continue/abort, hooks that modify messages or fail, signed commit cancellation, large history, submodules, LFS filters and an unavailable remote. These are validation proposals for the full build; none were executed during this documentation research.
